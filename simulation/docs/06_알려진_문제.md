# 06. 알려진 문제

상태 표시: **해결** / **부분 해결** / **미해결** / **확인 필요**

## 1. 벤치 찌꺼기 시뮬이 결과를 오염시킴 — 해결 (재측정 필요)

- **증상:** 실행 직후 바퀴 속도가 수천 rad/s로 튀고, 로봇 위치가 한 번에 1m 넘게 점프. 같은 조건인데 통과·실패가 뒤섞임.
- **원인:** 벤치는 실행이 끝나면 `ros2 launch` 프로세스 그룹에만 신호를 보냈습니다. 그런데 `ign gazebo`와 노드 일부는 다른 그룹으로 살아남았습니다. 모든 실행이 같은 ROS 도메인(77)과 Ignition 파티션(bench)을 쓰므로, 살아남은 시뮬이 `/ground_truth/odom`, `/joint_states` 등을 계속 보냈습니다.
- **확인:** 한 번에 `ps`로 보니 수 개의 `ign gazebo -s -r ...` 프로세스가 동시에 떠 있었습니다.
- **조치 (2026-10-15):** 벤치가 실행마다 환경변수 `PIPE_BENCH=<번호>`를 시뮬에 붙이고, 실행 전후로 이 표식이 있는 프로세스를 모두 종료하도록 고침.
- **검증:** 깨끗한 환경에서 pirate_v 직관 두 번 실행 → 둘 다 PASS, 미끄러짐 15.4% (기존 기준선과 같음).
- **영향:** 2026-10-15 이전의 모든 벤치 결과 (05 문서 표 참고).

## 2. 명시적 스프링이 불안정해 보였던 현상 — 확인 필요

- 처음 꼭짓점 토션 스프링을 넣었을 때 바퀴 속도가 폭주하는 것처럼 보였습니다. 그래서 `implicit_spring_damper`를 켰습니다.
- 그런데 증상이 1번 (찌꺼기 시뮬)과 같아서, 실제 원인은 **오염이었을 가능성이 큽니다.**
- `implicit_spring_damper=1`, `cfm_damping=1`은 Gazebo 예제 방식이라 예방 차원으로 남겨 두었습니다.
- 확인 방법: `pv2_*` 재측정에서 스프링 설정이 정상 주행하는지 보기.

## 3. 시뮬 실행 후 프로세스 남음 — 부분 해결

- 벤치 외에 수동으로 `ros2 launch`를 Ctrl+C로 끄면 `ign gazebo`가 남을 수 있습니다.
- 조치: 프로세스 정리 스크립트 (`scratchpad/kill_sim.sh` 형식) 또는 `ps -eo pid,args | grep -E "ign gazebo|lib/pipe_robot_sim"`로 확인 후 PID로 종료.
- 주의: `pkill -f "<패턴>"`은 패턴이 내 셸 명령에도 들어 있으면 **내 셸을 죽입니다** (종료 코드 144).

## 4. 화면 있는 실행은 느림 — 미해결 (설계 한계)

- Gazebo 창을 띄우면 실시간 대비 0.5~0.9배로 느려집니다.
- 벤치는 헤드리스로 돌아서 영향 없음. 화면 실행은 관찰용으로만 쓰세요.

## 5. ToF 센서는 렌더링이 필요 — 부분 해결

- `gpu_lidar` 센서는 디스플레이가 있어야 값을 냅니다. 디스플레이 없는 서버에서는 ToF 모델을 돌릴 수 없습니다.
- 벤치는 `DISPLAY`가 없으면 `:0`을 자동으로 씁니다 (창은 열리지 않음).

## 6. 화면에서 안이 보이게 하려고 배관을 자르면 센서도 잘린 벽을 봄 — 해결

- 화면 표시용 배관은 카메라 쪽 벽을 잘라 냈습니다.
- 센서는 잘린 벽을 뚫고 보는 문제가 있어, **센서 전용 완전한 배관**을 투명하게 겹쳐 두었습니다 (`visibility_flags 0x02`, 투명도 1.0).
- 확인: 센서 값이 화면 유무와 관계없이 같음 (배관 중심 거리 0.02~0.7 m 범위 측정).

## 7. 전체화면 창 — 부분 해결

- 이 PC에는 창 관리 도구 (wmctrl, xdotool)가 없습니다.
- 대신 Gazebo의 GUI 설정 파일을 복사해 창 크기를 1920×1050으로 바꿨습니다. 진짜 전체화면(F11)은 아닙니다.

## 8. 엘보에서 롤(비틀림)이 큼 — 미해결 (설계 과제)

- 좌우 엘보에서 특히 큼 (two_real 26~49°). 원인은 3륜 비대칭과 바퀴 속도 다툼.
- 시도한 것: 같은 토크 구동 (`diff`) — 오히려 악화. X자 4륜 — 좌우는 개선, 연속 엘보는 악화.
- 후보 (07 문서): IMU 롤 보정, 접촉력 기반 토크 분배, 무게중심 낮추기, 궤도.

## 9. 관절 서보 토크가 내리막에서 부족 — 부분 해결

- MG90S (0.21 N·m 가정)로는 내리막 90°에서 앞마디가 고꾸라졌습니다.
- 0.35 N·m (MG92B급 가정)로 올려 해결했지만, **실제 서보 토크는 아직 확인하지 않은 값**입니다 ([08 문서](08_추정값_목록.md)).

## 10. 궤도 플러그인이 배관에서 동작하지 않음 — 우회

- Gazebo Fortress의 TrackController/TrackedVehicle 플러그인은 배관 안에서 궤도 속도가 전달되지 않았습니다.
- 우회: 궤도 하나를 **일렬 구동 바퀴 4개**로 근사. 겉모양은 벨트. 실제 벨트의 미끄러짐·마찰과 다를 수 있습니다.

## 11. 오라클 제어는 실물 불가 — 설계 주의

- `three_segment`의 `follow_mode: oracle`과 `tracked`의 `oracle_steer`는 배관 중심선을 알고 제어합니다.
- 결과는 **상한값**입니다. 실물은 센서 기반 (`sensor` 모드)으로 평가해야 합니다.

## 12. 추정 파라미터가 많음 — 미해결 (실측 필요)

- 모터, 엔코더, 마찰, 질량, 서보 토크, 엘보 R 등 대부분이 추정입니다. 목록은 [08 문서](08_추정값_목록.md).
- 부품이 오면 실측값으로 바꾸고 재측정해야 합니다.

## 13. 바퀴와 배관 접촉 근사 — 참고

- 바퀴는 구(sphere) 충돌체, 배관은 박스 여러 개를 합친 메시로 근사합니다.
- 좁은 틈(바퀴와 벽 사이 1mm 수준)의 접촉 거동은 실물과 다를 수 있습니다.

## 14. 롤 기준 — 참고

- 롤 측정은 "배관을 따라 옮긴 위쪽 기준에서 몸통이 돈 각도"입니다. 직관에서는 위쪽 기준이 같으므로 0°가 나옵니다.
- 3D 코스(수직 포함)에서는 정의가 조금 복잡하므로 결과를 읽을 때 주의하세요.

## 15. 다른 모델 설정이 시험값으로 남아 있음 — 확인 필요

- `two_module/robot.yaml`의 `passive_k`가 0.3 (시험값). 기본은 0.01이었습니다.
- 사용할 일이 없다면 원래 값으로 되돌리거나 삭제하세요.

## 16. pirate_v 설정 파일이 스윕 중에 바뀜 — 확인 필요

- `bench/sweep_pv2.sh`는 실행 중에 `pirate_v/robot.yaml`을 바꾸고, 끝나면 시작 시점의 백업 (`bench/pv_yaml_backup2`)으로 되돌립니다.
- 스윕이 끝난 뒤 기본값은 일정 토크 모드 (`clamp_k: 0.0`, `clamp_torque: [0.15, -0.15]`)로 되돌렸습니다.
- 스윕 중에는 `pirate_v/robot.yaml`을 직접 고치지 마세요.

## 17. 기타 미구현

- T자 분기 (`T` 자 엘보)와 연속 엘보 코스는 아직 없습니다.
- 수직 등반 실험에서 배터리 무게 영향은 반영하지 않았습니다 (질량은 layout 기준으로 반영).
- 무선 통신, 탐촉자 측정 로직(펄서·수신 회로 시뮬)은 시뮬에 없습니다.
