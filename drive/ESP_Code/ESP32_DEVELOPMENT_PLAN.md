# 캡스턴 디자인 — ESP32 모터·인코더 개발 계획

작성일: 2026-11-16

> 진행 상태 업데이트 (2026-11-16): 사용자의 후속 요청에 따라 아래의 단계별 설명 방식 대신 소프트웨어 모듈을 한 번에 구현했다.
> 모터·인코더·PI·통신·타임아웃 공통 로직, Arduino-ESP32 연결부, PC 도구와 테스트가 추가되었다.
> 아래 본문은 초기 계획이며, 현재 구현과 실행 방법은 `README.md`를 기준으로 확인한다.

## 1. 목적과 현재 상태

배관 내부를 이동하는 뱀형 로봇의 바퀴 모터 구동과 인코더 측정을 ESP32에서 구현한다. 부품 도착 전에는 코드 구조, 명령 처리, 계산 로직과 빌드 환경을 준비하고, 도착 후 실제 배선과 회전을 검증한다.

현재는 설계·학습 단계다. 펌웨어 작성, 컴파일, 업로드 및 실물 검증은 아직 수행하지 않았다. 이 문서의 함수명과 폴더 구조는 제안이며 이미 구현된 기능이 아니다.

사용자는 C 학습 경험이 있으며, 코드를 이해하면서 함께 수정하기를 원한다. 코드를 한 번에 완성해 전달하지 말고 각 단계에서 **기능 설명 → 작은 코드 작성 → 코드 해설 → 검증** 순서로 진행한다.

## 2. 기준 자료와 확정 여부

기준 자료: `시뮬레이션_모델_부품_구성_(URDF).pdf` 1~4쪽.

- 모델 이름: `snake_v2`, PIRATE 방식의 뱀형 V자 차체.
- 이 PDF는 구매 확정 목록이 아니다. 크기·질량·성능에 추정값이 포함되어 있다.
- 전기·통신은 모델링하지 않았으며, 시뮬레이션이 동작했다는 사실이 실물 회로와 부품 성능을 보증하지 않는다.
- PDF에 기재된 관련 경로: `simulation/src/pipe_robot_sim/models/snake_v2/snake_v2.urdf.xacro`, `robot.yaml`. 실제 파일은 아직 열어보거나 검증하지 않았다.

## 3. 로봇 모델 구조

뒤에서 앞으로의 구성은 탐촉자 → 뒤 V팔(r1·r2) → 가운데 몸통 → 허브 → 앞 V팔(f1·f2) → 머리다.

| 위치 | 주요 구성 | 역할 |
|---|---|---|
| 꼬리 | 초음파 탐촉자, SG90, 자가 정렬 슈 | 배관 검사와 탐촉자 들어 올림 |
| 뒤 팔 r1 | MG90S J1, N20 w1 | 관절 굽힘과 바퀴 구동 |
| 뒤 팔 r2 | MG90S J2, N20 w2, DRV8833 | 관절 굽힘과 뒤쪽 바퀴 구동 |
| 가운데 몸통 | ESP32, MPU6050, 18650 셀 2개 | 하위 제어, 자세 측정, 주 전원 |
| 허브 | MG90S J3 | 몸 비틀기 |
| 앞 팔 f1 | MG90S J4, N20 w5, 강압 모듈 | 관절 굽힘과 바퀴 구동 |
| 앞 팔 f2 | MG90S J5, N20 w6, DRV8833, BMS | 관절 굽힘과 앞쪽 바퀴 구동 |
| 머리 | 상위 컴퓨터, 카메라·LED, ToF, MG90S J6 | 영상·거리 처리와 머리 굽힘 |

주요 모델 치수는 몸체 폭 28 mm, 팔 두께 24 mm, V팔 길이 85 mm, 머리 95 mm, 바퀴 지름 30 mm다. 모두 문서 기준이며 실제 제작 치수와 구분한다.

### 부품 구성과 문서의 미해결 문제

| 항목 | PDF 기준 | 개발 전 확인 사항 |
|---|---|---|
| 바퀴 모터 | N20 1:100 + 인코더, 목표 6개 | 실제 모델에는 4개만 배치, w3·w4 공간 미정 |
| 드라이버 | DRV8833 2개 | 독립 구동 모터 6개에는 3개 필요 |
| 인코더 | 2800카운트/회전 | 시뮬레이션 값. 실제 분해능·축 기준·계수 방식 확인 |
| 모터 성능 | 160 RPM, 스톨 토크 0.147 N·m | 추정값. 실제 모터 데이터시트 확인 |
| 모터 전원 | 모터 정격 6V, 배터리 2S 7.4V | 완충 전압과 모터용 전압 조정·전류 용량 확인 |
| ESP32 | 1개 | 보드·칩 모델, GPIO 및 PCNT/PWM 자원 미정 |
| 상위 컴퓨터 | Raspberry Pi Zero 2 W | 대체품 검토 중, 현재 모델 확정 안 됨 |
| 서보 | MG90S 6개, SG90 1개 | 바퀴 모터 코드와 분리하여 개발 |

문서에는 MG90S 실제 토크가 시뮬레이션 요구 토크보다 작다는 문제, V팔 무게 조건, 초음파 구동 회로 공간 미정, 전방 ToF 모델 표기 불일치도 있다. 바퀴 제어 코드가 완성되어도 이 기구·전장 문제는 별도로 해결해야 한다.

## 4. 장치별 역할

| 장치 | 역할 |
|---|---|
| 개발 PC | 코드 작성·빌드·업로드, USB 테스트 명령 전송, 로그 확인 |
| 상위 컴퓨터 | 향후 영상 처리·주행 판단, 모터 목표값 전송, 상태 수신 |
| ESP32 | 명령 해석, 모터 출력, 인코더 카운트·RPM 계산, 속도 제어, 통신 끊김 처리 |
| DRV8833 | ESP32 제어 신호에 따라 모터 전력의 방향과 공급 상태 변경 |
| N20 모터 | 전기 에너지를 회전으로 변환 |
| 인코더 | 축 회전을 A/B 신호로 전달 |

ESP32 GPIO는 모터 전력을 직접 공급하지 않는다. 모터 전력은 전원 → 드라이버 → 모터로 흐른다. 신호의 기준 전위, 인코더 출력 전압, 전원 분배는 실제 모듈 사양에 맞춰 설계한다.

초기 개발은 PC와 ESP32의 USB 시리얼로 진행한다. 최종 상위 통신 방식과 ROS/ROS 2 사용 여부는 미정이다. ROS를 사용한다면 일반적으로 ESP32가 모터 명령을 수신하고 인코더 상태를 송신하며, 상위 장치가 측정값을 구독한다. 처음부터 micro-ROS 사용을 확정하지 않는다.

## 5. 모터 구동 원리와 구현 범위

ESP32가 DRV8833 입력 두 개를 조절하여 모터 방향과 PWM 듀티를 정한다. PWM 듀티는 한 주기 중 구동하는 시간의 비율이며 실제 RPM 비율과 같지 않다.

| IN1 | IN2 | 기본 동작 |
|---|---|---|
| PWM | 0 | 한쪽 방향 구동 |
| 0 | PWM | 반대 방향 구동 |
| 0 | 0 | 코스트: 구동을 끊고 관성으로 감속 |
| 1 | 1 | 브레이크: 전기적 제동 |

드라이버 활성화 상태를 전제로 한 표다. nSLEEP 등 추가 핀의 노출 여부는 실제 모듈에서 확인한다. 전진의 부호는 배선과 장착 방향을 검증한 뒤 모터별 설정으로 정한다.

제안 API:

```cpp
setMotorPower(motorId, percent);  // -100~100 범위, 부호=방향
stopMotor(motorId, stopMode);    // 코스트/브레이크를 명시
```

처음에는 보수적인 출력 제한을 둔다. 급격한 방향 반전은 출력 감소와 정지 과정을 거치도록 한다. 출력 0은 순간적으로 축이 정지한다는 뜻이 아니다.

## 6. 인코더 측정 원리와 구현 범위

A/B 두 채널의 신호 변화 횟수로 회전량을, 변화 순서로 방향을 구한다. 일정 시간 동안의 카운트 차이를 속도로 변환한다. 실제 제품이 A/B 방식인지 먼저 확인한다.

```text
delta_count = current_count - previous_count
revolutions = delta_count / counts_per_output_rev
rpm = revolutions * 60 / elapsed_seconds
```

`counts_per_output_rev`는 현재 계수 방식에서 감속기 출력축 1회전당 얻는 카운트 수다. 엔코더가 모터축 기준이면 감속비를 반영해야 하고, 이미 출력축 기준이면 감속비를 다시 곱하면 안 된다. PPR/CPR 용어만으로 값을 확정하지 말고 x1/x2/x4 계수 기준을 확인한다.

예: 실제로 출력축 1회전이 2800카운트라고 검증되었을 때, 0.1초 동안 280카운트 증가하면 60 RPM이다. 2800은 예시와 시뮬레이션 값이며 실물 확정값이 아니다.

ESP32의 PCNT 하드웨어 사용을 우선 검토한다. 보드별 PCNT 수와 핀 조건을 확인한 후 최종 결정한다. CPU 인터럽트 방식은 대안이며 여러 모터의 최대 펄스율과 통신 부하를 고려한다. 최대 예상 계수율은 `counts_per_output_rev × max_rpm / 60`으로 산출한다.

측정 구현에서 확인할 항목:

- 빠른 펄스의 누락, 잡음 필터 설정, 정·역방향 부호.
- 카운터 오버플로 처리와 일관된 카운트 읽기.
- 고정 시간이라고 가정하지 않고 실제 경과 시간을 이용한 RPM 계산.
- 저속에서 카운트가 드문 경우의 속도 해상도와 필요시 필터링.
- 출력축을 여러 바퀴 돌려 1회전당 카운트 확인.

인코더는 축 회전을 측정한다. 바퀴 슬립이 있으면 회전 기반 이동 거리와 실제 이동 거리는 다르다. 초기 카운트 0은 소프트웨어 기준점이며 절대 위치를 뜻하지 않는다.

## 7. 두 제어 모드

| 모드 | 입력 | ESP32 동작 | 용도 |
|---|---|---|---|
| PWM 모드 | 부호 있는 출력 비율 | 지정 PWM 출력, 인코더 상태 보고 | 초기 구동·배선 검증 |
| RPM 모드 | 부호 있는 목표 RPM | 실제 RPM과 비교하여 PI/PID로 출력 조절 | 일정 속도 유지 |

RPM 제어는 목표값 수신 → 실제 RPM 측정 → 오차 계산 → 제어 출력 계산 → PWM 적용을 반복한다. 모터별 상태와 제어기 상태를 분리한다. 포화 시 적분 누적 방지, 정지·모드 전환 시 적분 초기화를 고려한다. 게인은 실물 시험으로 조정하며 시뮬레이션 수치를 그대로 적용하지 않는다.

## 8. 제안 코드 구조

ESP32 펌웨어는 C/C++을 사용하고 Arduino 기반으로 시작하는 안을 우선 검토한다. VS Code 빌드 도구와 보드 패키지 버전은 실제 보드 확인 후 결정한다. Python은 필요할 때 PC 테스트·그래프 도구에 사용한다.

| 제안 파일 | 책임 |
|---|---|
| `src/main.cpp` | 초기화, 비차단 반복 실행, 주기 작업 연결 |
| `include/config.h` | 핀·모터 개수·분해능·부호·주기·출력 제한 |
| `src/motor.cpp`, `include/motor.h` | DRV8833 출력과 정지 |
| `src/encoder.cpp`, `include/encoder.h` | 카운트 읽기, RPM 계산 |
| `src/communication.cpp`, `include/communication.h` | 명령 해석, 상태 전송, 타임아웃 |
| `src/speed_control.cpp`, `include/speed_control.h` | 이후 추가할 PI/PID |
| `tools/serial_test.py` | 선택 사항: PC 명령·로그 도구 |

처음부터 모든 파일을 구현하지 않는다. 모터 1개 기능부터 작성하고 이해한 뒤 분리한다. 통신 출력이 제어를 지연시키지 않도록 제어 주기와 상태 전송 주기를 구분한다.

### 테스트 통신 형식 제안 — 아직 확정 아님

```text
PWM 0 30       # 0번 모터 정방향 듀티 30%
RPM 0 60       # RPM 모드 구현 후 0번 모터 목표 60 RPM
STOP           # 전체 모터 정지
STATUS         # 상태 요청
```

모터 번호 범위, 수치 범위, 잘못된 명령, 긴 입력, 줄바꿈 처리를 정의한다. 상태에는 모터 번호, 시간, 모드, 목표값, 카운트, 실제 RPM, 출력, 오류를 포함한다. 타임아웃을 연장하는 유효 제어 명령 또는 heartbeat를 명시하고, 임의의 잘못된 데이터가 타임아웃을 연장하지 않게 한다. 현재 명령 예시는 실행 가능한 구현이 아니다.

## 9. 처음부터 포함할 동작

- 부팅·리셋 후에는 구동 출력을 끈 상태로 시작한다.
- 정해진 시간 동안 유효 제어 명령이 없으면 정지한다. 시간 값과 정지 방식은 시험 조건에 맞춰 확정한다.
- 잘못된 명령을 출력값으로 사용하지 않는다.
- 출력 제한과 점진적인 출력 변경을 적용한다.
- STOP은 모든 모터에 적용한다. 소프트웨어 STOP은 물리적 전원 차단을 대신하지 않는다.
- 통신 복구만으로 이전 출력이 자동 재개되지 않게 하고 새 명령을 요구한다.
- 인코더 이상 판정은 저속·정지 상태와 구분하여 이후 추가한다. 전류 센서 없이 과전류를 소프트웨어가 직접 측정한다고 가정하지 않는다.

| 7 | 여러 모터 확장 | 모터별 독립 제어, 동시 구동 시 카운트·전원·주기 확인 |
| 8 | 상위 장치 연동 | 합의된 명령·상태 형식으로 연결 및 끊김 시험 |

부품 도착 전: 설정 구조, 명령 파서, 가상 카운트에 대한 RPM 계산, 빌드까지 준비 가능하다. 부품 도착 후: 실제 핀과 신호 레벨, 회전 방향, 전류·발열·전원 강하, 펄스 누락, RPM 제어 게인을 확인한다. 하드웨어가 없으면 실물 검증 완료라고 기록하지 않는다.

## 11. 아직 필요한 정보

- ESP32 정확한 보드·칩 모델과 핀맵.
- N20 제품 링크, 정격 전압, 무부하·정격·스톨 전류, 감속비, 속도.
- 인코더 전원·출력 전압, 출력 회로 방식, 신호선, 분해능 정의.
- DRV8833 모듈 핀맵, 전류 제한 설정 및 실제 연속 구동 가능 전류.
- 실제 구동 모터 개수와 기구 배치 확정.
- 모터·ESP32·서보 전원 분배, 강압 장치 용량.
- 최종 상위 컴퓨터, 통신 방식, ROS 사용 여부.
- 6개 모터·7개 서보·센서·통신을 포함한 전체 GPIO/PWM/PCNT 자원 예산. 단일 ESP32로 충분하다고 미리 확정하지 않는다.

## 12. 다음 Codex 세션에서 이어갈 작업

이 문서와 부품 PDF를 먼저 읽고, 현재 폴더의 실제 파일 상태를 확인한다. 이미 작성된 코드가 있으면 보존하고 구현 상태를 파악한다.

첫 작업은 **모터 1개 기준 배선 요구사항과 `setMotorPower()`의 동작 설명**이다. 보드와 제품 사양이 없으면 임의의 핀이나 2800카운트를 확정값으로 쓰지 않는다. 설정 미정과 실행 가능한 코드를 명확히 구분한다.

2. 입력·출력과 단위는 무엇인가?
3. 어느 핀 또는 상태를 바꾸는가?
4. 어떻게 실행하고 정상 여부를 확인하는가?
5. 아직 검증하지 못한 것은 무엇인가?
